# 旅摊摊 iOS App PRD 初稿

版本：v0.3  
日期：2026-06-02  
状态：待对齐

## 1. 产品定位

旅摊摊是一个面向朋友、同学、情侣、家庭出游的 iOS 共享记账 App。核心场景是大家一起旅行、露营、聚餐或短途出行时，记录共同开销，并在活动结束后自动算清每个人应该补给谁多少钱。

第一版的重点不是个人财务管理，而是让多人共同消费这件事变简单：

1. 一次旅行对应一个共享账本。
2. 每个人输入用户名即可进入 App，通过账本邀请码加入同一个账本。
3. 每个人都可以实时登记支出。
4. 每笔支出默认由登记人付款，并由账本内所有成员分摊。
5. 系统自动汇总人均、个人应付、个人已付和最终结算建议。

## 2. 目标用户

### 主要用户

- 几个人一起出去玩，需要分摊吃饭、住宿、交通、门票等开销。
- 每个人都可能负责登记自己支付的开销，希望大家共同维护同一个账本。
- 不想用 Excel 或群消息手动对账的小团队。
- 希望在手机上随手记录，而不是回家后凭记忆补账的人。

### 非首版重点用户

- 严肃个人理财用户。
- 公司报销和发票管理用户。
- 长期家庭账本用户。
- 大型团队、俱乐部或复杂 AA 制平台用户。

## 3. 用户问题

1. 旅行中开销频繁，群里转账和聊天混在一起，事后很难对账。
2. 不是每笔钱都所有人平摊，比如有人没参加某顿饭、情侣两人算一份、有人先垫付。
3. 多个人都可能付钱，活动结束后手算“谁欠谁”很麻烦。
4. 旅行中网络可能不稳定，记账流程不能依赖复杂操作。
5. 大家不想走复杂注册流程，但愿意输入一个用户名来标识自己。
6. 大家希望通过邀请码快速加入同一个账本，而不是手动同步数据。

## 4. 产品目标

### MVP 成功标准

- 用户可以创建一个旅行账本。
- 用户可以输入用户名完成轻注册。
- 用户可以通过账本邀请码加入旅行账本。
- 账本成员可以实时看到其他成员新增、编辑、删除的支出。
- 用户可以记录一笔支出，包括金额、登记人/付款人、分类、时间、备注。
- 用户可以查看旅行总支出、成员已付、成员应付、成员净额。
- 用户可以生成最少转账次数的结算建议。
- App 重启后仍能通过本地会话进入自己的账本。

### 第一版非目标

- 不做复杂个人收支管理。
- 不做预算、资产、收入、投资等理财功能。
- 不做微信、支付宝账单自动导入。
- 不做发票和报销流程。
- 不做多币种汇率自动换算。
- 不做复杂权限系统。
- 不做手机号、邮箱、短信验证码、OAuth 等正式账号体系。
- 不做离线多人冲突合并。离线时可以查看本地缓存，但新增/编辑支出需要联网。

## 5. 核心概念

### 5.1 旅行账本 Trip

一次旅行、一次聚餐或一次活动就是一个账本。

字段包括：

- 名称：例如“青岛周末旅行”。
- 开始日期。
- 结束日期，可选。
- 默认货币：第一版默认 CNY。
- 成员列表。
- 支出列表。
- 邀请码。
- 状态：进行中 / 已结束。

### 5.2 用户 User

用户打开 App 后，只需要输入一个用户名即可完成轻注册。

字段包括：

- 用户 ID。
- 用户名。
- 创建时间。
- 最近活跃时间。

第一版不要求手机号、邮箱和密码。服务端创建用户 ID，客户端保存用户 ID 作为本地会话凭证，下次打开 App 直接进入账本列表。

### 5.3 成员 Member

成员代表一个用户在某个账本里的身份。

字段包括：

- 用户 ID。
- 账本 ID。
- 展示名称，默认等于用户名。
- 头像颜色或首字母。
- 加入时间。
- 状态：active / removed。

通过邀请码进入账本后，用户会自动成为该账本成员。

### 5.4 邀请码 Invite Code

每个账本生成一个短邀请码，用于让其他用户加入。

要求：

- 创建账本后自动生成邀请码。
- 创建者可以复制邀请码。
- 其他用户输入邀请码后加入账本。
- 第一版邀请码长期有效，不做过期时间。

### 5.5 支出 Expense

支出是一笔共同消费。

字段包括：

- 金额。
- 登记人：创建这笔支出的成员。
- 付款人：第一版默认等于登记人。
- 参与分摊成员：第一版默认账本内所有成员。
- 分摊方式：第一版固定均分。
- 分类：餐饮、交通、住宿、门票、购物、其他。
- 日期时间。
- 备注。

第一版只做正向支出，不做收入、退款、优惠、押金退还等反向流水。退款和抵扣放到第二阶段专门支持，避免 MVP 结算逻辑过早复杂化。

后加入账本的人也参与此前所有支出的分摊。也就是说，第一版的分摊对象不是“支出创建时的成员快照”，而是“当前账本内 active 成员全集”。如果后续需要更精细的场景，再支持按单排除成员或固定历史参与人。

### 5.6 结算 Settlement

系统根据所有支出计算：

- 每个成员已付金额。
- 每个成员应承担金额。
- 每个成员净额：已付 - 应付。
- 谁应该转给谁多少钱。

结算建议应尽量减少转账次数。例如 A 多付 100，B 少付 60，C 少付 40，则建议 B 转 A 60，C 转 A 40。

## 6. 核心功能

### 6.1 轻注册

用户首次打开 App 时输入用户名即可完成轻注册。

必填：

- 用户名。

交互要求：

- 用户名不能为空。
- 用户名不要求全局唯一。
- App 请求服务端创建用户 ID，并把用户 ID 保存在本机作为会话凭证。
- 用户后续可以修改展示名称。

### 6.2 创建旅行账本

用户可以创建一个新账本。

必填：

- 旅行名称。

可选：

- 日期。

交互要求：

- 创建流程要短，优先让用户快速进入账本。
- 创建者自动加入账本成员。
- 创建成功后自动生成邀请码。
- 账本详情页展示邀请码复制入口。

### 6.3 通过邀请码加入账本

用户可以输入邀请码加入别人创建的账本。

流程：

1. 用户输入邀请码。
2. App 请求服务端校验邀请码。
3. 校验成功后，将当前用户加入账本成员。
4. 用户进入账本首页，并拉取账本当前数据。

异常处理：

- 邀请码不存在：提示“邀请码无效”。
- 网络不可用：提示“当前无法加入账本，请稍后再试”。
- 用户已在账本中：直接进入账本。

### 6.4 账本首页

账本首页展示当前旅行的核心信息：

- 旅行名称。
- 邀请码复制入口。
- 总支出。
- 人均支出。
- 当前用户净额，如果能识别当前用户。
- 最近支出列表。
- 新增支出入口。
- 结算入口。

如果用户还没有录入支出，显示空状态，引导新增第一笔支出。

账本首页需要实时更新。当其他成员新增、编辑或删除支出后，当前用户应在短时间内看到变化。

### 6.5 新增支出

用户可以记录一笔共同支出。

字段：

- 金额：必填。
- 付款人：第一版默认登记人，不提供修改入口。
- 参与分摊成员：第一版固定为当前账本所有 active 成员，不提供选择入口。
- 分类：默认“餐饮”或“其他”。
- 日期：默认当前时间。
- 备注：可选，例如“第一天晚饭”。

交互要求：

- 金额输入优先弹出数字键盘。
- 金额输入支持快捷四则运算，例如 `100+20/2`，保存前计算为最终金额。
- 表单应显示“付款人：我”和“分摊：账本内所有成员”，让默认规则可见。
- 保存后回到账本首页或支出列表，并显示新记录。
- 保存成功后，其他在线成员也能看到这笔支出。

### 6.6 支出列表与详情

账本内按时间倒序展示支出。

列表展示：

- 分类。
- 备注或分类名。
- 付款人。
- 登记人。
- 当前分摊人数。
- 金额。
- 日期。

详情页展示：

- 完整金额。
- 登记人。
- 付款人。
- 当前每个 active 成员应分摊金额。
- 备注。
- 创建/更新时间。

用户能力：

- 编辑支出。
- 删除支出。

第一版允许账本成员编辑和删除账本内任意支出，不做复杂权限控制。详情页需要展示最后修改时间，帮助成员判断信息是否被更新。

### 6.7 成员管理

用户可以在账本内管理成员。

第一版能力：

- 通过邀请码加入成员。
- 查看成员列表。
- 修改自己的展示名称。
- 查看成员统计。

第一版不提供移除成员能力。因为按当前规则，所有 active 成员都会分摊所有支出，移除成员会直接影响历史结算。成员移除、退出账本和历史分摊冻结放到第二阶段设计。

### 6.8 结算页

结算页展示：

- 每个成员已付金额。
- 每个成员应付金额。
- 每个成员净额。
- 建议转账列表。

示例：

```text
小李 转给 小王 128.50 元
小张 转给 小王 72.00 元
```

交互要求：

- 金额保留两位小数。
- 净额为正表示“应收”，净额为负表示“应付”。
- 结算建议可以复制为文本，方便发到群聊。

### 6.9 实时多人编辑

第一版支持账本成员实时共同编辑。

要求：

- 任意账本成员都可以新增支出。
- 任意账本成员都可以编辑或删除账本内支出。
- 支出变更同步到服务端。
- 其他在线成员在短时间内看到更新。
- 如果两个成员同时编辑同一笔支出，第一版采用最后写入覆盖，并记录 `updatedAt`。
- 客户端以服务端数据为准。

### 6.10 分享账本

第一版分享能力包括：

- 复制账本邀请码。
- 复制结算结果文本。
- 分享账本摘要文本。

## 7. 分摊规则

### 第一版支持

- 均分：账本内所有 active 成员平均承担金额。
- 后加入成员也分摊加入前已存在的支出。

### 第二阶段可支持

- 排除成员：某笔支出可以只让部分成员参与分摊。
- 自定义金额：每个人承担不同金额。
- 自定义比例：例如情侣两人算一份。
- 多付款人：一笔支出由多人共同垫付。
- 退款/抵扣：例如退押金、优惠券、取消订单。
- 历史成员快照：某笔支出只由当时账本内的成员分摊。

第一版先把“所有成员均分”做好，牺牲一部分灵活性，换取最快的输入速度和最简单的结算逻辑。

## 10. 结算计算逻辑

### 10.1 单笔分摊

对于一笔金额为 `amount` 的支出：

- 付款人的已付金额增加 `amount`。
- 账本内所有 active 成员平分 `amount`。
- 每个 active 成员应付金额增加 `amount / active 成员数`。

后加入成员也会参与所有历史支出的分摊，因此结算结果会随着成员数量变化而变化。

### 10.2 成员净额

```text
净额 = 已付金额 - 应付金额
```

- 净额 > 0：这个人多垫了，应收钱。
- 净额 < 0：这个人少付了，应补钱。
- 净额 = 0：已经平衡。

### 10.3 转账建议

将成员分为：

- 债权人：净额为正。
- 债务人：净额为负。

用双指针或贪心算法匹配债务人和债权人，每次生成一笔转账，直到所有净额接近 0。

金额精度：

- 展示保留两位小数。
- 内部建议用 Decimal，避免浮点误差。
- 对不可整除的分摊，最后一分钱可以按成员排序补齐，保证总额一致。

## 11. 技术方向建议

### 第一版推荐

- SwiftUI：开发 iOS 原生界面。
- SwiftData 或本地缓存：缓存用户会话和最近账本数据。
- 服务端 API：保存用户、账本、成员、支出和结算相关数据。
- 实时同步通道：WebSocket、Server-Sent Events 或轮询，第一版可从简单轮询开始。
- Foundation Decimal：处理金额。
- 后端数据库：保存共享账本数据，服务端数据为准。

### 首版运行目标

- iOS 17 或更高版本。

理由：SwiftData 从 iOS 17 开始可用，适合第一版缓存用户会话和最近账本数据。共享账本的权威数据仍以服务端为准。

### 实时协作路线

第一版需要真正的多人共同编辑。每个用户输入用户名完成轻注册，通过邀请码进入账本，所有成员都能新增、编辑、删除支出。

同步实现可以分阶段：

1. MVP 可用方案：客户端定时轮询账本变更，例如每 3 到 5 秒拉取一次。
2. 更好体验：使用 WebSocket 或 SSE 推送账本变更。
3. 后续增强：加入离线编辑队列、冲突提示和权限控制。

当前 PRD 建议第一版采用“服务端保存 + 客户端轮询”的实时协作 MVP，先降低实现难度；后续再升级到 WebSocket/SSE。

## 12. 隐私与数据

第一版需要服务端保存共享账本数据，客户端本机只保存用户会话和最近访问账本的缓存。

需要在 App 中明确说明：

- 用户只需输入用户名，不需要手机号、邮箱或密码。
- 账本数据会保存到服务端，用于多人实时共享。
- 邀请码可让其他人加入账本，用户应只把邀请码发给同行成员。
- 删除 App 不会删除服务端账本，但如果本地用户 ID 丢失，用户可能无法用原身份继续操作，需要后续提供找回能力。

## 14. 已确认决策

1. 同一账本内用户名必须唯一，避免成员列表和结算页混淆。
2. 邀请码使用 6 位字母数字码，例如 `A7K2Q9`。
3. 第一版允许任何账本成员编辑或删除任何支出。
4. 金额四则运算支持 `+ - * /`、小数和括号。
5. 第一版只支持人民币 CNY，不做多币种。
6. 第一版后端使用 Python FastAPI。
